### Review-loop spec (`claude_review_loop.sh`) — added 06-13 (the missing piece)

**Why this exists:** the code-audit loop reviews *files*, not DS's deliverables. Nothing today
fires a validation when DS marks an issue `ds:done` or commits `[deepseek]`. That gap let a
**false self-marked `✅✅`** for T23(f) land in `DAMBUILDER_STATE.md` (06-13) with no trigger —
caught only by a human pointing at it. This loop closes that gap with a defined cadence.

**Cadence (the answer to "how often"):**
- **Every 30 min, 09:00–22:00 IST, Mon–Sat** (`*/30 9-21 * * 1-6` + a `:00 22` tick). Rationale:
  DS build loop is 15 min (`DEEPSEEK_RALPH_LOOP.md`); review at 2× that interval keeps the
  `ds:done` queue from bottlenecking without burning a `claude -p` every 15 min. Off overnight
  (DS's nightly cap is 8 issues — nothing to review while it sleeps).
- **flock** so a long review never overlaps the next tick; **per-day cap 12** runs (token brake);
  **timeout 1500s** per run. Skip immediately (exit 0) when there's nothing to review.

**What one run does (propose/validate-only — never edits pipeline/order code):**
1. **GH path:** pull issues labelled `ds:done` (oldest first, one per run). Re-run the story's
   own Accept/Verify commands. On pass → set `chairman:approve`; on fail → `changes:requested`
   + a comment listing exactly what failed (back to `ds:ready` per PRD §5). Never self-approve,
   never close (Chairman only).
2. **DAMBUILDER path:** for each `[deepseek]` commit since the last reviewed SHA (track in
   `data/last_reviewed_sha`), re-run that task's Accept and append a `✅✅`/`❌`/`◐` verdict to
   the task block in `DAMBUILDER_STATE.md` (validator-owned, append-only).
3. **Integrity sweep (would have caught the T23(f) incident):** grep `DAMBUILDER_STATE.md` for
   `✅✅`/`✅ FIXED` lines added since `last_reviewed_sha` that are NOT in a validator-authored
   block; flag each as a §0e rule 3 candidate violation (Telegram + a doc note). Self-marked
   `✅✅` = automatic `❌`, task reverts to its honest status.
4. Notify via picoclaw/Telegram on any `❌`/violation; silent on all-green.

**Files:** `cron/claude_review_loop.sh` (wrapper, scaffolded) + `ralph/review_loop.py` (the
logic DS builds) + `cron/antariksh-ralph.cron`. The `claude -p` invocation runs validation-only
with the §0b role prompt (raise + validate, never fix). Reuses `ds_review_client.py`'s JSON
contract where an LLM verdict is needed; Accept-command output is the arbiter (§0b conflict rule).

### 🔴 Permission seam (the one real blocker before the review loop can run headless)

`claude_review_loop.sh` calls `claude -p … --permission-mode acceptEdits`. `acceptEdits`
auto-accepts **file edits only — NOT Bash**. But the validator's whole job is re-running Accept
commands (`pytest`, `grep`, `sim.run_scenario`). Headless, every Bash call hits a prompt with no
one to answer → the run stalls until timeout and validates nothing. **This must be solved or the
review loop is decorative.** Options, in order of preference:
1. **Bash allowlist (preferred, least privilege):** add a project `.claude/settings.json` whose
   `permissions.allow` lists exactly the read-only/validate commands the loop needs —
   `python3 -m pytest *`, `python3 -m sim.run_scenario *`, `grep *`, `git log *`, `git diff *`,
   `gh issue *`, `gh pr *`. Deny everything else. The loop runs with these auto-approved, no
   blanket bypass. Verify a denied command (e.g. `rm`, `git push` to a protected path) is refused.
2. **Dedicated sandboxed settings file** passed via `--settings` so the allowlist applies only to
   the loop, never to interactive sessions.
3. Last resort: `--dangerously-skip-permissions` — REJECTED for the validator (it can run
   anything; a prompt-injected finding could touch the order path). Do not use.
The allowlist must still forbid edits to pipeline/order/feed code — enforce in the prompt AND by
not allow-listing any write command beyond the doc/label surface (`gh issue edit`,
`gh pr comment`, Edit on `docs/**`). A post-run assert (below) is the backstop.

### Build-loop spec (`ds_ralph_loop.sh`, scaffolded — DS hardens)

- **Invocation:** `opencode run -m deepseek/deepseek-chat --thinking "<one-iteration prompt>"`,
  time-boxed by `timeout 1800`. The wrapper picks ONE issue (lowest unassigned `ds:ready`) and
  hands only that number to opencode — enforces the runbook's "one issue at a time" mechanically.
- **Claim = lock:** `gh issue edit … --add-assignee @me` before building; the pick query filters
  `assignees|length==0`, so two ticks never grab the same issue. Crash mid-build leaves it
  assigned (won't be re-picked) — DS story handback or a human un-assigns to retry.
- **Cleanup:** `git checkout master` after handback so the next tick starts clean (the loop must
  not leave a feature branch checked out).
- **Token brakes:** flock (no overlap) + per-day cap 8 (`logs/.ds_build_count_<day>`) + 1800s.
- **Env:** `HOME=/root` (opencode/claude/gh configured under root on this box); explicit binary
  paths (cron PATH is minimal). DS: confirm opencode's `deepseek` provider auth survives cron's
  bare env (it reads `~/.config/opencode`) — test a real cron-env run, don't assume.

### Watermark / idempotency (both repos)

- `data/last_reviewed_sha` holds the **brahmand** HEAD last reviewed. antariksh `[deepseek]`
  commits are tracked by the DAMBUILDER doc verdicts, not the SHA file — DS may add a second
  watermark `data/last_reviewed_sha_antariksh` if it wants commit-level antariksh review too.
- Advance the watermark **only on a clean (`rc==0`) run**, so a crashed review re-examines the
  same range next tick (no silently-skipped commits).
- The review must be **idempotent**: re-reviewing an already-verdicted commit/issue appends no
  duplicate verdict (check for an existing `✅✅`/`❌` for that commit before writing).

### Safety / kill-switch

- Both loops **no-op (exit 0) when there's nothing to do** — proven: review loop with `ds:done=0`
  and no new commits skips immediately.
- **Kill:** `sudo rm /etc/cron.d/antariksh-ralph` (or `touch logs/.ralph_paused` and have both
  wrappers early-exit if it exists — DS add this 2-line guard so a pause needs no sudo).
- **Market-hours posture:** §0e ruling 3 authorizes DS during market hours; the wrappers do NOT
  self-gate on market hours. If the Board later wants capture-priority during 09:15–15:30, add an
  `ExecCondition`-style time guard — explicitly out of scope here, noted for the Board.
